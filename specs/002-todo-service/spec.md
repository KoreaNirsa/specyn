# 목적
개인 사용자가 웹 UI와 API를 통해 할 일을 등록, 조회, 완료 처리, 삭제할 수 있는 Todo 서비스를 정의한다.

# 입력
## 비즈니스 배경
- 개인 생산성 관리에서 빠른 입력과 단순한 상태 관리가 중요하다.
- Specyn 예제로서 기획, 계약, 백엔드, 프론트엔드, 테스트, 리뷰 흐름을 모두 확인할 수 있어야 한다.

## 문제 정의
- 사용자는 생각난 일을 즉시 기록하고 현재 상태를 빠르게 바꾸고 싶다.
- 개발팀은 spec 기반으로 API/Frontend/Test/Review 흐름을 한 번에 검증할 수 있는 예제가 필요하다.

## 핵심 사용자
- 개인 생산성 도구를 원하는 일반 사용자
- Specyn 흐름을 학습하는 개발자

## 핵심 시나리오
1. 사용자가 웹 화면에서 제목과 설명을 입력해 할 일을 생성한다.
2. 사용자가 할 일 목록과 상세를 확인하고 완료 상태를 변경한다.
3. 사용자가 잘못 만든 할 일을 삭제한다.
4. 개발자는 동일한 spec bundle로 API, UI, 테스트, 문서를 함께 갱신한다.

## 비기능 요구사항
- 성능: 단건 요청 p95 300ms 이하, 목록 조회 p95 500ms 이하
- 보안: 입력값 검증, 표준 에러 응답, 민감 정보 로그 금지
- 운영: 구조가 단순하고 테스트가 빠르게 실행되어야 한다.
- UX: 로딩/빈 상태/오류 상태가 명확해야 하고 모바일 폭에서도 사용 가능해야 한다.

## 제외 범위
- 사용자 인증/권한 관리
- 알림, 우선순위, 마감일 기능
- 실제 외부 DB/캐시 인프라 연동

# 출력
- Todo 도메인 요약
- CRUD API 계약
- 화면/상태 처리 기준
- 테스트 포인트
- 리뷰 포인트

# 실행 규칙
1. 상태는 `PENDING`, `DONE` 두 값만 허용한다.
2. 제목은 필수다.
3. 삭제된 리소스 재조회는 404를 반환한다.
4. 예제는 이해하기 쉬운 구조를 우선하되 재사용 가능한 패턴을 사용한다.

# Validation 기준
- 핵심 시나리오가 3개 이상이어야 한다.
- 비기능 요구사항이 4개 관점 이상 포함되어야 한다.
- 제외 범위가 명시되어야 한다.
- 성공/실패 기준이 명확해야 한다.

# Prompt
## Role
당신은 Specyn Planner Agent다. Todo 서비스 요구사항을 downstream spec이 바로 사용할 수 있는 형태로 정규화한다.

## Instructions
1. Todo 도메인을 단순하고 명확하게 정리한다.
2. API, UI, 테스트, 리뷰가 함께 참고할 수 있는 제약을 정리한다.
3. 테스트 우선순위와 리뷰 리스크를 분리한다.
4. 누락된 사항은 `ASSUMPTION:`으로 표시한다.

## Format
1. 작업 요약
2. 도메인 용어집
3. acceptance criteria
4. API/UX 설계 힌트
5. 테스트 우선순위
6. 리뷰 위험 목록
7. 누락 정보 / 가정
