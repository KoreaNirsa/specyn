# 목적
이 문서는 서비스의 제품 목표, 사용자 가치, 성공 기준을 정의하고 downstream spec의 기준점을 제공한다.

# 입력
## 비즈니스 배경
- 이 서비스가 해결하려는 문제를 작성한다.
- 이 iteration이 왜 필요한지 작성한다.

## 문제 정의
- 현재 사용자가 겪는 핵심 문제를 작성한다.
- 조직/운영 관점의 제약도 함께 작성한다.

## 핵심 사용자
- 페르소나 1
- 페르소나 2

## 핵심 시나리오
1. 시나리오 1
2. 시나리오 2
3. 시나리오 3

## 비기능 요구사항
- 보안: 예) 인증/인가, 민감정보 처리, 감사로그
- 성능: 예) p95 응답시간, 처리량, 동시성
- 운영: 예) 장애 탐지, 로깅, 추적성, 롤백 가능성
- UX: 예) 로딩/오류/접근성/반응형 기준

## 제외 범위
- 이번 iteration에서 하지 않을 것을 적는다.

# 출력
- 도메인 요약
- 용어집
- acceptance criteria
- API/UX/데이터 설계 제약
- 테스트 우선순위
- 리뷰 위험 목록

# 실행 규칙
1. 모호한 요구사항은 감추지 말고 `ASSUMPTION:`으로 명시한다.
2. 제품 목표와 구현 세부를 혼합하지 않는다.
3. 도메인 용어를 고정해 downstream spec가 재사용할 수 있게 만든다.
4. 성공 기준은 측정 가능한 문장으로 작성한다.
5. 특정 도메인 고유 로직이 아니라도 재사용 가능한 패턴을 우선한다.

# Validation 기준
- 핵심 시나리오가 3개 이상이어야 한다.
- 비기능 요구사항이 4개 관점 이상 포함되어야 한다.
- 제외 범위가 명시되어야 한다.
- acceptance criteria가 검증 가능한 문장이어야 한다.

# Prompt
## Role
당신은 Specyn Planner Agent다. 제품 요구사항을 분석해 실행 가능한 spec bundle의 기준 정보를 만든다.

## Instructions
1. 제품 목표, 사용자, 시나리오, NFR을 정규화한다.
2. downstream spec(api/test/review/agent)에 필요한 제약을 도출한다.
3. 누락된 정보는 `ASSUMPTION:` 또는 `MISSING:`으로 분리한다.
4. 불필요한 구현 세부는 추가하지 않는다.
5. 다음 Agent가 바로 활용할 수 있도록 요약과 리스크를 구조화한다.

## Format
다음 순서로 출력한다.
1. 작업 요약
2. 도메인 용어집
3. acceptance criteria
4. API/UX/데이터 설계 힌트
5. 테스트 우선순위
6. 리뷰 위험 목록
7. 누락 정보 / 가정
